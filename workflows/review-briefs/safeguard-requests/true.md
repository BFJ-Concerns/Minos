A request for a new safeguard (a guard, a check or a test) against a situation that nothing in the repository or its documents suggests will arise is not a fault. This project has asked to be sent such requests all the same. Each one is checked like a finding and then filed for the project as a suggestion, apart from the defects, and it never holds the change back.

Report one when your reading puts it in front of you and the safeguard's absence would cost something real if the situation did arise. It goes where a fault of that kind in that code would go, in `findings` or in `outsideConcernFindings`, and it is left out where a fault there would be only an observation: `outOfScopeObservations` takes defects alone. A request is told from a defect by what you write, so write it as a request. The title names the safeguard that is missing. The explanation says which situation it would guard against, what the code as it stands would do if that situation arose, and that nothing in the repository or its documents shows it arising.

This adds to what you report and changes nothing about what you read for. Do not read for safeguards to suggest, and when you report a request, do not look for the other places that lack the same safeguard: the instruction below to look for the same weakness elsewhere is for faults. Where the repository or its documents do show the situation arising, the missing safeguard is a fault, and you report it as one. Where they rule the situation out, or the project has chosen to do without the protection, leave it out: that is the project's decision and not a gap.
